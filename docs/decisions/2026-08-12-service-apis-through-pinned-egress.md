# ADR-0096: Сервисные API через закреплённый egress, ключ — только заголовком

- **Статус:** Принято
- **Дата:** 2026-08-12
- **Связано:** ADR-0094 (чтение произвольной страницы), ADR-0010 (egress-политика),
  ADR-0027 (сужение возможностей при untrusted-контексте)

## Контекст

В каталоге ключей ([service-keys.ts](../../packages/app/src/service-keys.ts))
оператору предлагаются Serper («нормальный поиск»), Supadata («транскрипты
видео») и Apify («скрейперы для площадок, которые не отдают данные»). Ключи
принимались, проверялись, сохранялись — и не читались никем: `web_search` ходил
в бесплатный DuckDuckGo-парсер, а `fetch_url` всегда пытался прочитать сырой
HTML, которого у страницы видео или закрытой ленты просто нет.

Это то же самое, чем были таймеры до `set_trigger`: обещание в интерфейсе без
реализации за ним. Оператор вводит ключ, видит «✅ Сохранил» и не получает
ничего.

Технически всем трём мешало одно: закреплённый egress умел ровно один вид
запроса — `GET` с фиксированными заголовками. Serper — это `POST` с
`X-API-KEY`, Apify и Supadata — Bearer и `x-api-key`. Отправить учётные данные
было нечем.

## Решение

**Транспорт получает метод, заголовки и тело. Все остальные проверки остаются
на месте, а ключ ходит только заголовком.**

### Что добавлено

`PinnedHttpsRequest` получает `method` (`GET` | `POST`), `headers` и `body`;
рядом с `makePinnedHttpsTextGet` появляется `makePinnedHttpsJson` — та же
последовательность проверок, но ответ разбирается как JSON.

Неизменным остаётся всё, что и было границей: только https, без порта и
credentials в URL, DNS закреплён на адрес, к которому реально подключается
сокет, приватные и loopback-диапазоны отвергаются, тело ответа ограничено,
дедлайн общий на запрос, список хостов 1..32.

### Собственные границы нового пути

- **Заголовки — по имени из списка:** `authorization`, `x-api-key`,
  `content-type`, `accept`. Ни `cookie`, ни подмена `user-agent`. Значение без
  управляющих символов и переводов строки: заголовок с CRLF — это попытка
  расщепления запроса, и она не доходит до сокета.
- **Ключ — только в заголовке.** Query-строка оседает в логах на той стороне,
  поэтому JSON-путь дополнительно прогоняет query через тот же детектор
  секретоподобных строк, что стоит на поисковом запросе. Apify принимает
  `?token=`, и мы этой возможностью сознательно не пользуемся.
- **Тело** ≤ 32 КБ, только вместе с `POST`, с явным `content-length` в байтах.
- **Редиректы не отслеживаются.** Для страницы редирект — норма (ADR-0094), для
  API — признак сломанного endpoint, а не переезда.

### Маршрутизация решается кодом, а не моделью

Модель по-прежнему знает два инструмента: `web_search` и `fetch_url`. Какой
сервис отвечает, выбирает [link-services.ts](../../packages/app/src/link-services.ts)
по хосту ссылки: видео → Supadata, площадка с логин-стеной → Apify,
всё остальное → прямой закреплённый fetch. Агент, выбирающий между Apify и
прямым запросом, выбирал бы за счёт, которого не видит.

Нет ключа — ответ не «не смог», а предложение с адресом экрана: «⚙️ Настройки →
🔑 Ключи сервисов → 📹 Supadata». Каталог ключей и инструменты наконец
ссылаются друг на друга.

Подтверждение домена не меняется: `fetch_url` остаётся tier 2, карточка
называет домен ссылки (ADR-0094), а не сервис, через который она читается.

### Бесплатное первым, платное последним

Дополнение от 2026-08-12 по результатам проверки бесплатных дорог.

Перед любым платным сервисом стоит бесплатный ридер (`r.jina.ai`): он открывает
страницу у себя, отдаёт её текстом и переводит в текст документ, который наш
процесс прочитать не может. Ключа он не требует. Порядок дорог:

1. прямой закреплённый fetch;
2. бесплатный ридер — если страница пришла пустой (её рисует скрипт) или
   сервер вернул не текст (PDF, офисный документ);
3. платный Apify — только если ридер отказал;
4. честный отказ с адресом экрана ключей.

Ридеру отдаётся **только** ссылка, которую прямой путь отверг по содержимому:
`EGRESS_RESPONSE_DENIED`, `EGRESS_RESPONSE_INVALID`, `EGRESS_RESPONSE_TOO_LARGE`.
Отказ по адресу — запрещённый URL, приватный диапазон, несостоявшийся DNS —
наружу не передаётся никогда: сервис, который ходит по ссылке за нас, иначе
стал бы обходом той самой проверки. Ссылка пересобирается по тем же правилам,
что и для прямого пути (только https, без порта, логина и фрагмента).

Тонкий ответ ридера считается отказом, а не содержимым: логин-стена — это тоже
текст, и отдать её модели значит выдать закрытую страницу за прочитанную. Порог
тот же, по которому страница признаётся пустой оболочкой.

Это решение снимает с плана отдельный headless-браузер в контейнере: рендер
происходит на чужой стороне, а 1.9 ГБ памяти сервера не делятся с Chromium,
который OOM-killer обменял бы на самого агента. Свой браузер остаётся нужен
только для страниц за личным логином оператора — это отдельная тема с хранением
учётных данных.

### Дополнение от 2026-08-31: бесплатный поиск через RSS Bing

Проверка на production показала, что HTML-выдача DuckDuckGo отвечает кодом 202
и защитной страницей без результатов независимо от User-Agent. Одновременно
обычный HTTPS с того же хоста работает, а RSS-выдача Bing на `www.bing.com`
отвечает XML с результатами. Это не запрет сети и не повод просить оператора
менять режим безопасности: прежний бесплатный endpoint перестал выполнять
свой продуктовый контракт.

При отсутствии ключа Serper `web_search` теперь обращается к exact-host
`www.bing.com:443` с `format=rss`. Поисковая строка проходит прежнюю проверку
на размер, управляющие символы и секретоподобные данные; DNS, закрепление IP,
TLS-имя, remote-IP, дедлайн и размер ответа не меняются. Транспорт принимает
для этого пути только ограниченный XML/RSS-текст, а чистый parser возвращает
ту же внутреннюю форму `title/url/snippet`. Ключ Serper по-прежнему имеет
приоритет и не меняет интерфейс инструмента.

## Последствия

### Положительные

- Три обещанных ключа начинают работать, закрывая соцсети, видео и качественный
  поиск без единого мегабайта памяти на сервере.
- Одно расширение транспорта покрывает все три сервиса и любой следующий.
- Ключ структурно не может попасть в URL: путь, который его туда положил бы,
  отвергается детектором.

- PDF и офисные документы по ссылке читаются, хотя сам процесс их разбирать не
  умеет и зависимости для этого не заводит.
- Оператор без единого ключа получает страницы, которые рисует скрипт, и
  документы — платные дороги нужны только для остатка (видео, логин-стены).

### Цена

- Ссылка и содержимое уходят третьей стороне. Для платных дорог это осознанный
  обмен: оператор сам подключает ключ, зная, чей это сервис. Для бесплатного
  ридера ключа нет, поэтому и согласия им не выражено — ссылка уходит туда
  молча. Дорога включается только там, где прямой путь уже провалился, то есть
  вместо отказа, а не вместо прямого чтения; но это остаётся именно ценой.
- Бесплатный ридер — внешний сервис с лимитом на анонимные запросы. Он может
  отказать в любой момент; тогда маршрут просто идёт дальше по списку.
- Форма ответов сервисов не под нашим контролем. Разбор защитный: неожиданная
  форма даёт понятный текст, а не исключение.
- Появился второй способ выйти наружу — JSON-путь. Он ограничен списком хостов
  в композиции (`SERVICE_HOSTS`) и не принимает произвольный адрес от модели.

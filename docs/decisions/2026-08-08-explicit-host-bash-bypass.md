# ADR-0091: Явный durable-режим полного host Bash

> **Поправка от 2026-08-09.** [ADR-0092](./2026-08-09-plan-mode-research-then-execute.md)
> меняет только прежнюю семантику `plan` из пункта 5: после исследования план
> выполняется автоматически. Контракт полного host Bash `bypass` не изменён.

**Статус:** Принято
**Дата:** 2026-08-08
**Теги:** safety, bash, ux

## Контекст

ADR-0083 разрешает режимам исполнения только ужесточать code-owned проверки.
Это удобно для повседневной работы, но не покрывает отдельную установку Aisy на
сервере, где оператор сознательно хочет дать агенту полный shell-доступ: текущий
host-адаптер отклоняет часть команд, убирает credential-shaped environment и
всё равно проходит общий approval/HARD_DENY gate.

Оператор выбрал явный режим `bypass`. В обычной работе нужны предупреждения и
существующие ограничения; при осознанном включении `bypass` нужен настоящий
host Bash без подтверждений Aisy. Режим должен переживать restart и оставаться
включённым до ручного `/mode auto`.

## Решение

Добавить четвёртый режим исполнения `bypass`, который точечно пересматривает
bash-часть ADR-0011, ADR-0047 и ADR-0083.

1. `bypass` действует только на runtime tool `bash`. Остальные инструменты,
   бюджеты, capability scopes и протоколы не получают обхода. Режим действует
   для основного агента, его фоновых и goal-ходов, а также подписочного мозга.
   Дочерний агент не получает произвольный Bash: его scoped executor не умеет
   доказать, что shell соблюдает `owns/doNotTouch` из Agent Card.
2. В `bypass` вызов `bash` не проходит HARD_DENY, narrowing, tier/grant и
   Telegram approval. Host-адаптер не применяет command denylist. Рабочий
   каталог остаётся Workspace, но абсолютные пути доступны в пределах прав
   системного пользователя Aisy.
3. Режим не повышает OS-права, не выдаёт root и не настраивает sudo. Если
   системный пользователь уже имеет passwordless sudo, shell сможет его
   использовать — это часть принятого оператором риска.
4. Лимит времени и объёма возвращаемого вывода остаётся как защита живости
   harness, фильтрация credential-shaped environment и post-tool redaction —
   как защита секретов и журнала. Они не ограничивают, какие файлы или команды
   доступны shell; секреты подключаются через отдельные broker-инструменты.
5. `auto`, `confirm` и `plan` сохраняют прежнюю семантику. UI постоянно и
   недвусмысленно показывает, что обычный Bash ограничен, а `bypass` даёт
   полный доступ к хосту.
6. Выбор durable: успешное включение публикуется только после fsync и атомарной
   записи приватного состояния schema v2, поэтому переживает restart. Перед
   любой сменой с участием `bypass` создаётся отдельная durable-метка безопасного
   режима. Пока переход не завершён, её наличие запрещает восстановление
   `bypass`; поэтому сбой во время `/mode auto` немедленно закрывает новые полные
   Bash-вызовы и не может вернуть опасный режим после restart. Неизвестная
   версия, повреждённый файл, symlink или слишком широкие права также дают
   безопасный non-bypass fallback. `bypass` действует до явного переключения
   оператором, рекомендуемый выход — `/mode auto`.
7. Переключение доступно только через аутентифицированный операторский Telegram
   transport. Модель не получает отдельного tool для смены режима.
8. `/mode auto` закрывает новые bypass-вызовы немедленно, но не убивает уже
   запущенный процесс. Для остановки текущей команды используется штатная
   отмена turn/restart; скрытый `kill` при смене режима не вводится.

## Последствия

- **Положительное:** на выделенном сервере агент может без карточек выполнять
  администрирование, работать с любыми доступными файлами и запускать обычные
  системные инструменты.
- **Положительное:** опасный режим виден как отдельное состояние и не маскируется
  под `auto`; выход из него — одно явное действие.
- **Нейтральное:** режим относится только к Bash. Например, платёжный или MCP
  tool не становится разрешённым из-за `bypass`.
- **Отрицательное:** ошибка модели или prompt injection в этом режиме имеет тот
  же blast radius, что и ручная shell-команда системного пользователя Aisy.
- **Отрицательное:** когда управляющий процесс и shell работают под одним UID,
  предупреждения и denylist обычных режимов не являются границей против
  намеренно враждебного процесса. Для такой угрозы нужен отдельный worker UID,
  контейнер или внешний policy broker; этот ADR их не заявляет.

## Рассмотренные альтернативы

**Полный Bash в `auto`.** Отклонено: опасное состояние было бы неотличимо от
обычной работы, а случайный restart мог бы неожиданно расширить доступ.

**Подтверждать каждую команду.** Уже есть `confirm`, но он делает автономное
администрирование выделенного сервера практически бесполезным.

**Обязательный Docker для всех команд.** Даёт сильную границу, но не позволяет
управлять широким host-файловым деревом и сервисами. Docker остаётся для
специальных sidecar; оператор сознательно принимает host-risk в `bypass`.
